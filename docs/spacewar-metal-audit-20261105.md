# Spacewar Metal jitter and latency audit — 5 November 2026

The later [combined fixes and canvas correction](spacewar-metal-fixes-20261105.md)
resolve the touch, cached-shader, padded-constant and source-reuse findings below.
The user confirmed the scale-2 canvas smooth with correct layout after the
retained MobileGestalt scale was refreshed. This page preserves the earlier
audit evidence; physical scanout synchronization remains open.

The extra framebuffer presentation beat is a confirmed contributor. With
`fb_beat=0`, the user reported **“Noticeably smoother”**. Its measured wait
fell from a 7.11 ms median to zero. The phone remains on that RAM test.
This establishes a useful improvement, not a complete rendering or latency fix.

The display-use ownership candidate did not resolve the user's complaint.
Other measured costs remain in GPU rendering, CPU encoding, shader compilation
and physical touch delivery. There is also a confirmed skipped-draw defect.
This audit covers the boot/display handoff, CPU and memory policy, touch,
Metal compilation and submission, surface ownership, scaling, presentation,
and the measurement tools.

## Findings

### 1. Presentation adds another clock and delay

`xnu/files/iokit/Kernel/MiniIOMobileFramebuffer.cpp`, `show()`, schedules an
adaptive beat after the GPU wait. It aims for a fraction of a period and
adjusts phase as frames arrive; missing the beat can add almost another period.
The 7.11 ms median wait is directly visible in `tl: v` timestamps.

The inspected traces have no `tl: y` despite tracing being enabled.
`userland/src/inject.c` explains that this iPhone X configuration normally uses
Core Animation's own `CADisplayTimer`; `ca_vbl=1` would select driver callbacks.
There is no demonstrated synchronization between CA's timer, the presenter
beat and physical scanout. The existing `fb_ca_hz=120` control can investigate
CA's documented half-advertised-rate behavior without claiming the panel is
running at 120 Hz. It has not been physically compared in this audit.

Normal Metal profiles generated by `tools/spacewar-metal-package.py` now use
the user-confirmed `fb_beat=0`. The twelve explicit comparison profiles retain
the original baseline and individual changes. Kernel-wide and Redwood defaults
are unchanged.

### 2. GPU work exceeds a 60 Hz frame budget

Hardware pass timestamps, unlike the old aggregate “GPU busy” label, show
fullscreen 18-draw sysmem passes taking 20.62–21.49 ms in the baseline.
The ownership run includes a 19-draw pass at 16.81 ms. This is real execution
cost before presentation and cannot be fixed by surface reference counts.

`hakios-metal/src/render.cpp` selects GMEM using a 56-draw threshold and recent
draw-count history. That branch bypasses the cost tuner. Pixel coverage,
fragment shader cost and framebuffer feedback can make a low-draw-count pass
expensive. Conversely, idle ten-draw passes take only about 0.05 ms, so forcing
all work through GMEM is not justified.

Bounded next comparisons are a lower threshold and the existing cost tuner.
The tuner requires **both** `metal_gmem=1 metal_gmem_draws=0`; setting the latter
alone disables GMEM in the plug-in. Those controls are not in the current
Spacewar live-loader allowlist and were not silently enabled. Preserve the
v15 framebuffer-fetch ordering fix when investigating GPU costs.

### 3. CPU encoding and shader compilation add separate stalls

An active baseline reporting window averages 150.5 draws per buffer at
51 microseconds per driver draw, about 7.7 ms of encoding before other CA work.
Current profiles have deferred recording disabled. Redwood's common runner
enables it. A deferred-recording experiment must retain the scheduled-handler
submission drain so SwapEnd observes the current surface fence.

Cold shader specializations commonly take 220–346 ms, with a 699 ms outlier.
Until a specialization is ready, the plug-in uses the much larger original
fragment shader. Persistence does not imply that every needed variant is
already cached.

There was also a concrete locking defect: `compileStage()` acquired the global
compiler lock before looking for a cached stage. A synchronous cache hit could
wait behind an unrelated asynchronous compilation. The new
`include/hakios-metal/compiler_cache.hpp` protocol separates cache I/O from
Mesa's compiler lock and rechecks the cache after a miss acquires that lock.
Compilation remains serialized; duplicate simultaneous misses do not compile
twice. Deterministic threaded tests cover both properties and fail when the
old locking or missing recheck is substituted.

This fix is built and packaged separately. It is **not on the currently running
phone**, so it does not explain the user's unpaced improvement. Its compiler
fingerprint changes; cached stages/seeds need warmup or regeneration. The host
suite lacks native Mesa libraries, so host cache serialization is not claimed
as exercised; the real Mesa-enabled arm64 compiler and plug-in build succeeded.

### 4. Some compositor draws are actually skipped

The unpaced log records 20 refusals for `fixed_vert_lph_spc` with
`fixed_frag_lph_cph`: buffer 3 has 48 bytes left in its allocation, while the
pushed constant range requests 64 bytes. The extracted vertex AIR under
`build/spacewar-metal-20261105/failing-pair/vertex.ll` reads only one float4,
16 bytes, from that buffer. Its 64-byte matrix is in buffer 2.

Mesa pads the upload range. `render.cpp`, `pushedRanges()`, rejects the padded
range when it crosses the mapped allocation boundary. Non-strict command
buffers skip the draw and continue; there is no fallback renderer for it.
Passing pipeline creation and alpha probes therefore does not establish full
compositor correctness.

The correction needs a bounded, padded staging range while preserving the
execution ordering of GPU-written uniforms. Simply relaxing the bounds check
would permit an out-of-allocation read. This remains an identified defect;
the compiler-cache candidate does not change it.

### 5. Physical touch has its own cadence and release problem

Across 36 physical strokes in the fresh ownership audit:

| Input interval | Median | p95 |
| --- | --- | --- |
| DOWN → first MOVE | 20.02 ms | 24.52 ms |
| MOVE → MOVE | 22.75 ms | 32.86 ms |
| Last MOVE → UP | 100.45 ms | 109.76 ms |
| Kernel post → input read | 0.031 ms | 0.140 ms |
| Input read → event dispatch | 0.144 ms | 0.627 ms |

The earlier baseline has the same approximately 100 ms release pattern.
Physical finger-lift time is unmeasured, so the last row of a stroke is not a
direct finger-lift latency measurement. Its consistency strongly implicates
the FT12 driver's 100 ms high-IRQ fallback.

`drivers/input/hakios.goodix.c`, `spacewar_ft12_poll()`, hard-codes 8 ms sleeps
and that fallback. It **does not read `touch_poll_us`**; the configurable loop
is the separate generic Goodix path. Spacewar reads each 62-byte report through
a 71-byte GPIO SPI transaction, with 1,136 one-microsecond delay calls and a
loader ownership lease. Reading, lease waiting and scheduling add to the
fixed sleep. USB log transfers can affect lease availability.

No controller-read timing trace currently separates IRQ observation, lease
request/grant, wire transfer and post. Add those measurements and include a
USB-quiet interval before changing polling/fallback policy. The ~8 ms cadence
in the original one-gesture ownership capture came from synthetic `rwtouch`,
which bypasses this physical input path.

### 6. Surface ownership and physical scanout are still incomplete

The `fb_surface_use` candidate balances display-use counts through queued GPU
waits and copy completion. It advertises a reader to cooperating producers;
it does not enforce exclusion against GPU writes. `SwapWait` still supplies
no completion tracking. `MiniIOSurfaceDrawn()` waits a mutable surface-wide
fence, not an immutable fence captured for a particular swap.

With default `fb_filter=2`, moving frames use nearest-neighbor scaling and slow
frames use filtering. Nonintegral scaling can make edges step unevenly. The
delayed settle path reacquires a released live surface after 40 ms, checks its
`drawn` value once, then copies without write exclusion. Submission after that
check is a real race. Fast/slow classification also uses time since the last
copy **finished**, which can misclassify backlogged frames.

The existing `filtered` control removes the delayed settle path by filtering
every frame, but may cost more CPU time. It remains a separate comparison.
An extra fence wait alone cannot eliminate submission after the wait.

The driver copies into the retained ABL framebuffer while scanout can read it;
there is no atomic page flip. Spacewar's physical panel mode/rate is not yet
measured. ROM panel candidates declare command mode, but that does not identify
the active bootloader configuration. Redwood's video-mode beam counter must
not be assumed to apply. `tl: v` cannot certify tear-free scanout.

### 7. Redwood is a materially different workload and platform setup

The supplied device tree was inspected at
[`04fbfff933f52faf203a55aca9dd5680092e6ec5`](https://github.com/oosexgang/hakios-sm7325/tree/04fbfff933f52faf203a55aca9dd5680092e6ec5).
Its stale device-status description is not evidence about the user's actual
Redwood Metal binary. The common runner shows these differences:

| Area | Current Spacewar test | Common Redwood runner |
| --- | --- | --- |
| Virtual rendering size | 1125 × 2436 | 750 × 1624 through `fbscale=2` |
| CPU allocation | Seven XNU CPUs, CPU0 retained by loader | Eight CPUs |
| CPU policy | Bounded 1900/1862 MHz requests on domains 1/2 | Reference-board boost path |
| DDR bandwidth | Inherited; CPU-only path skips voting | MC0/SH0 bandwidth votes in `cpufreq=1` path |
| Copy workers | Three | Six |
| Recording/wallpaper | Deferred off; wallpaper not frozen | Deferred on; wallpaper frozen |
| Touch transport | FT12 GPIO SPI plus resident-loader lease | Different controller/transport path with 4 ms polling setting |
| Display | Retained bootloader buffer; active mode unmeasured | Reference platform and runner's 120 Hz assumptions |

Spacewar renders exactly **2.25 times as many source pixels**. One tightly packed
RGBA plane is 10.962 MB versus 4.872 MB; repeated full-screen feedback/overdraw
multiplies this difference. Lower virtual resolution would not reduce the
physical 1080 × 2400 output-copy size.

In five active ownership windows, 1,173 submissions over 25.086 seconds average
12.92 ms of hardware GPU execution and 0.700 ms of CPU cache maintenance per
submission. Cache work is measurable, but substantially smaller than GPU work.
The 12,901 KiB cache statistic is logical range coverage, **not measured DRAM
traffic**. DDR saturation remains an unmeasured hypothesis.

Source inspection found cached IOSurfaces/client pages and write-combined
ordinary GPU allocations/framebuffer output, not an obvious Device-memory
framebuffer mistake. Removing coherency operations would risk stale pixels.
Spacewar's CPU branch also bypasses the reference memory benchmark and CPU-load
setup; simply adding those boot arguments would not activate them.

GPU startup measured 550 MHz. Logs show the requested CPU rates and temperatures
around the 50s Celsius during interaction, without a captured thermal stop.
Those observations do not independently measure effective CPU clocks or exclude
all firmware throttling. No captured GPU timeout or panic establishes the jitter
as a GPU hang.

### 8. Diagnostics previously understated or mislabeled the delays

`tools/frames.py` used to omit every gap of 100 ms or more. It now retains gaps
overlapping observed contacts, including 222 ms and 251 ms in the fresh audit
and a 555 ms gap in the baseline. Other long gaps are explicitly unclassified
because animation state is unknown. Thresholds now display their actual
18/34.5 ms tolerances, and output says framebuffer copies rather than physical
panel frames.

Metal `tl: M` records are now summarized independently. The `gpu` field is host
commit-to-fence observation, including queueing, submission and scheduling.
Summing overlapping buffers can exceed 100%; that was never measured GPU
utilization. The plug-in's old zero-FPS message counted `presentDrawable`, which
CA's IOMFB route does not use. Its labels now explain both facts.

`tools/latency.py` now labels recorded-content lag relative to posted input,
reports available input/copy stages without GLES traces, and leaves physical
scanout and application scheduling unknown. It no longer assumes 120 Hz or
subtracts unrelated stage averages to invent application latency.

The diagnostic profiles enable detailed logging and repeated USB snapshots.
The earlier user-confirmed quiet GLES build disabled those diagnostics. Logging
and lease contention need a quiet control before attributing every tail to the
renderer. Frame-copy telemetry also excludes subsequent recording, release
and retained-allocation clearing, so that work can appear in later queue time.

## Delivered changes and remaining work

The running, user-confirmed improvement is the original v15 core with unpaced
presentation: `ram-bundle-final/metal-unpaced/metal-unpaced-debug.bin`.
Normal future packaged Metal profiles select that same presentation policy.
No boot partition was flashed.

The separately built compiler-cache candidate is
`native-metal-cache-fix/manifest.json`, with matching payloads in
`ram-bundle-cache-fix/bundle.json`. It keeps the existing kernel, GMEM threshold,
disabled deferred recording, shader specialization and v15 feedback ordering.
It passes 263 host tests, the actual arm64 core/plug-in build, APFS readback,
payload/loader policy checks and packaging. Its phone behavior remains untested.

Seven frame-analysis regressions cover missed stalls, multiple contacts,
truncated traces, duplicate snapshots, Metal attribution and actual thresholds.
Four latency-output regressions and eight exact-source acceptance tests pass.
The display-use regression still passes. The current unpaced phone run passes
seven pipeline cases, 18 scheduling cases and all three nine-case alpha modes;
these tests do not cover the newly identified constant-buffer boundary defect.

The next work is deliberately separated by cause: constant-buffer staging for
skipped draws; FT12 timing and release fallback; warmed compiler-cache comparison;
then individually controlled deferred-recording, GMEM and virtual-resolution
tests. Physical scanout synchronization and the settle race require their own
correct ownership design. The user-confirmed pacing improvement should be kept
while those remaining issues are addressed.
